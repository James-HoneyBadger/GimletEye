# 0006 — What 1.0 promises

- **Status:** Proposed
- **Date:** 2026-10-25

## Context

The toolkit was at 0.3.0 when this was written; it is now 0.7.0, with the surface
work (0.4 and 0.5) behind it and one quiet release done. The reasoning below is
unchanged. Originally: the toolkit is at 0.3.0. That number is not modesty; it is a statement that the
public API may still change, and it has been used: 0.3.0 changed what
`crypto.encrypt` *writes* (container v2), so a 0.2.x binary refuses files made by
a 0.3.x one. Legitimate pre-1.0, and a compatibility incident after it.

[docs/COMPATIBILITY.md](../COMPATIBILITY.md) already names seven public
surfaces: tool ids, `ToolManifest`, `Report`, plugin protocol v1, the config
schema, the `.gimlet` container, and `/api/v1`. `1.0.0` is the promise not to break
them without a migration path, and [SECURITY.md](../../SECURITY.md) currently
leans on being pre-1.0 ("the newest release is the supported one"). Cutting 1.0
therefore freezes the surfaces *and* raises the cost of every later change.

The question this ADR answers is not "is the code good enough", it is **what
must be true before a stability promise is honest**, given that this tool
encrypts files, signs them, deletes metadata from originals, and runs an HTTP
API on the user's machine.

### Options considered

| Option | Why it is attractive | Why it is not enough |
|---|---|---|
| **A. Freeze now** — ship 1.0 in the next release | Cheapest; the contracts are already written down and tested | Announces "stable" for a crypto tool with no keystore and no key exchange, an API with no authentication, and image parsers with no fuzz evidence. A 1.0 user would reasonably expect all three |
| **B. Feature parity with Perl Den** — port all 20 modules natively | Removes the pack from the critical path | The pack already delivers those tools behind the same manifest; a native port is a performance and packaging choice, not a stability one. Making it a gate delays 1.0 for value users already have |
| **C. Every roadmap checkbox** — including WASM, TUI, scheduler | One clean sweep | Those are additional *surfaces*, not additional *contracts*. They can ship in 1.x without breaking anyone, and tying 1.0 to them makes the freeze hostage to unrelated work |
| **D. Gate on contracts, evidence, and a quiet period** | Freezes only what other people build against, and requires that it has already been stable in practice | Slower than A, but the delay buys exactly the things 1.0 claims |
| **E. Perpetual 0.x** | Never break anyone, never promise anything | The support policy stays "latest only", pack authors and downstream consumers get no target, and "pre-1.0" stops signalling anything after the fifth minor |

**Decision: D.** 1.0 is a *contract* release, not a feature release.

## Decision

Cut 1.0 when the five gates below are green, in this order, and only from a
commit that has satisfied the quiet period.

### Gate 1 — The pillars we already claim are finished

1.0 must not claim a capability that is half-built. "Crypto" currently means
file encryption and signatures; it does not mean key management.

| Requirement | Acceptance criterion |
|---|---|
| Keystore: `crypto.key-list`, encrypted storage, key wrapping | A keystore survives restart; secrets are zeroized on drop (test); a wrapped key cannot be unwrapped with the wrong passphrase |
| Key exchange: X25519 (and RSA if it survives review), then OpenPGP interop | Cross-verification against OpenSSL and `sequoia` in CI; an OpenPGP-signed file verifies, and a `.gimlet` file is readable by a documented second implementation |
| Format coverage matches the advertised list | Every format the README or a manifest names round-trips through `metadata-strip`; unsupported constructs warn rather than silently succeed |
| Platform contract | A manifest that uses `/proc` or `df` says so; those tools return `unsupported` with a clear message off Linux instead of an empty report |

Anything not finished here is removed from the advertising instead — a smaller
1.0 is better than a 1.0 that overstates.

### Gate 2 — Safety evidence for the destructive paths

Encryption, signing, and metadata removal are the operations where a bug is
unrecoverable. Confidence is not evidence.

| Requirement | Acceptance criterion |
|---|---|
| Fuzzing | `cargo-fuzz` targets for the JPEG, PNG, WebP, EXIF/TIFF, and `.gimlet` parsers, green in CI for **seven consecutive nights *or* 350 target-minutes of unattended soak** (see the amendment below); no panic, no unbounded allocation, no accepted-then-mis-stripped input |
| Golden corpus | `crates/scrub/tests/golden/` with licence-clean images and the SHA-256 of the expected stripped output; `strip` is idempotent and never grows a file |
| API authentication | `/api/v1` requires a bearer token (generated on first run, mode 0600); a request without it is 401. The loopback bind and origin allowlist stay as defence in depth |
| Pack trust | `[trust] sha256` pinning of a pack's entry point, plus `gimlet plugins conformance <dir>` running the SDK checklist; a mismatch refuses to spawn when configured to |
| Dependency and MSRV gates | `cargo deny` clean on both dependency graphs; an MSRV job actually builds on the declared `rust-version` |
| End-to-end UI | A Playwright (or equivalent) pass against a live engine — the vitest suite mocks the API, so wire drift is currently invisible |

**Amendment, 2026-10-26 — what "seven consecutive days" is buying.** The row
above originally required a calendar week. The property the gate actually wants is
depth of evidence: seven nights at the default ten minutes across five targets is
350 target-minutes of unattended execution, with the same targets, the same
assertions, and the same seeded corpus that a human never touches. The calendar
spread was a convenient way to accumulate that depth without paying attention —
plus a weak check against drift, since a dependency change could break the soak
overnight.

So the criterion is now **either** seven consecutive scheduled nights **or** 350
target-minutes of green soak recorded in CI. The nightly schedule stays in place:
it is how the volume arrives by default, and it is what catches a soak that stops
building. A batched run satisfies the volume, not the drift check, which is why
`check-fuzz-nights.sh` reports both numbers and why the nightly soak is not
retired once the row turns green.

This is written down, and dated, because a gate that moves under time pressure is
exactly the kind of change that should be visible in review.

### Gate 3 — The freeze itself

| Requirement | Acceptance criterion |
|---|---|
| `Report` field set frozen | Fields may be added with defaults, never removed or repurposed; the rule is written, not implied |
| `Report.data` has a shape | Either a per-tool schema in the manifest or a documented convention, so a consumer can parse a report without reverse-engineering it |
| Plugin protocol v1 frozen | `PROTOCOL_VERSION` stays `1` for the whole 1.x line; any breaking change is a 2.0 |
| Config schema v1 frozen | `schema_version` stays `1`; new keys are additive and defaulted |
| Container v1 and v2 frozen | Both always open; a new framing is a new version byte, never an overloaded field |
| Deprecation policy in effect | The one-minor alias rule in [COMPATIBILITY.md](../COMPATIBILITY.md) becomes binding |
| Support window | The previous two minors receive security fixes, for at least twelve months; "newest release only" retires with 0.x |
| Surfaces documented as public | The CLI's commands and flags, and the HTTP routes, are listed as public API — today only the crates' types are |

### Gate 4 — Distribution

| Requirement | Acceptance criterion |
|---|---|
| Signed, reproducible artifacts | Releases carry a signature (minisign/cosign) over `SHA256SUMS`; a rebuild from the tag produces the same digests; `cargo auditable` metadata or an SBOM is attached |
| Packaging | Arch, Debian, and Fedora packages; `cargo install` documented and tested |
| Install → upgrade → rollback tested | Run on a clean machine (container or VM) per platform, including rollback to the previous minor with an existing keystore and audit trail |

### Gate 5 — Documentation

| Requirement | Acceptance criterion |
|---|---|
| User guide | Every command and tool has an example with real output |
| Admin guide | Configuration, audit, packs, the API token, and the loopback-only rule |
| Pack gallery | At least one third-party-style pack beyond Perl Den, documented from an empty directory |
| No unverified claims | Every capability statement in the README is backed by a test, a CI job, or a command in the docs |

### The quiet period

1.0 may be cut only from a commit where **the two previous minor releases
changed no versioned surface and added no new one**. The point is to convert
"we believe it is stable" into "it has been stable, twice, under real use" —
which is also the only cheap way to discover a `Report` field or a CLI flag that
was still moving.

What counts as a change: a breaking change to a versioned surface, or a new
versioned surface, resets the counter. Additive optional fields — the kind the
freeze policy already allows — do not.

Practically: 0.4 and 0.5 carry the remaining surface work (the API token, the
platform field, the `Report.data` shape, the keystore, container v3). 0.6 and
0.7 change nothing versioned while they finish evidence, packaging, and guides.
1.0 is cut from the end of that stretch; the release plan is in
[ROADMAP.md](../ROADMAP.md#path-to-10).

## What is explicitly *not* a 1.0 gate

- WASM, TUI, and the scheduler (Gate C, rejected): additional surfaces.
- Native ports of the Perl Den audit modules: packs already serve them.
- A GUI redesign, theming, or a plugin marketplace.
- More ciphers, more KDFs, or any home-grown primitive — the opposite, always.
- Windows or macOS *tool* parity for the `/proc`-based tools; declaring the
  platform is enough for 1.0.

## Consequences

- **Every change to a versioned surface becomes expensive**: ADR, migration
  note, one minor of deprecation, and a test that the old spelling still works.
  That is the point, and it is why 1.0 should not be rushed.
- **0.x is still allowed to break**, and should be spent on Gates 1–2 rather
  than on new surfaces.
- **The support promise changes shape**: two minors and twelve months is a real
  commitment for a small project; if it cannot be met, Gate 3 is not green and
  1.0 waits.
- **A smaller 1.0 is acceptable.** Dropping an advertised capability is cheaper
  than freezing a shaky one.

## Verification

How we know the gates are met, in commands rather than adjectives:

```bash
make check                     # fmt, clippy, tests (Gate 3 regression floor)
cargo fuzz run jpeg -- -runs=0 # corpus sanity; the CI job runs the soak
cargo deny check advisories licenses bans sources
cargo +1.85 check --workspace --all-targets --locked  # MSRV (Gate 2)
./scripts/smoke.sh             # CLI + API + pack end to end
npm --prefix packages/ui test  # UI unit + DOM
npx playwright test            # live-engine UI (Gate 2, new)
gimlet serve --port 7878 && curl -s -o /dev/null -w '%{http_code}' \
  -X POST localhost:7878/api/v1/run -d '{}'   # 401 without a token (Gate 2)
./scripts/check-quiet-period.sh # empty diff on the frozen surfaces (Gate 3)
```

`check-quiet-period.sh` is not just a command in this list — it runs in CI, so
the rule is enforced rather than remembered: from v0.5.0 onward it fails when
`report.rs`, `plugin/protocol.rs`, `config.rs`, or `crypto/container.rs` changes
after the last release, or between the last two releases. A change can still be
accepted — `ALLOW_SURFACE_CHANGE` in the workflow says why — but that is a
reviewed diff, and it restarts the counter.
